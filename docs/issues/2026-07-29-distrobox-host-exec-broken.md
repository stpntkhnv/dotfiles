# Сломано выполнение команд на хосте из контейнера

Найдено 29 июля 2026 при проверке hostового herdr. Отложено, не чинилось.

## Симптом

Внутри `digi3`:

```sh
distrobox-host-exec echo hi
# rc=127, ни строчки вывода
host-spawn echo hi
# rc=127, ни строчки вывода
```

`/usr/bin/host-spawn` на месте (3.8 МБ, 28 июля), `/usr/bin/distrobox-host-exec`
тоже. То есть падает не отсутствие бинаря.

## Почему это важно

`home/.chezmoiscripts/run_onchange_after_37-container-links.sh.tmpl:30` ставит
в контейнер обёртку `xdg-open`, которая для http(s) делает

```sh
exec distrobox-host-exec /usr/local/bin/zen-open "$ctx" "$1"
```

Значит любая ссылка, открытая изнутри рабочего контейнера, до хостового
браузера сейчас не доезжает. Отказ молчаливый: обёртка просто вернёт 127.

Это ровно тот режим отказа, против которого написан весь остальной репозиторий.

## Зацепка

`DBUS_SESSION_BUS_ADDRESS` в контейнере равен `unix:path=/run/user/1000/bus`,
унаследован с хоста. Но `/run/user/1000` внутри контейнера **не хостовый**: там
свой набор файлов, хостового сокета herdr, созданного в тот же день, там нет.
host-spawn общается с хостом через session bus, так что первое, что стоит
проверить, это существует ли `/run/user/1000/bus` внутри и куда он ведёт.

Хостовый `/run/user/1000` при этом достижим по пути
`/run/host/run/user/1000/`, что проверено отдельно.

## Как проверить, что починилось

```sh
distrobox enter digi3 -- distrobox-host-exec id -un     # должно печатать stsiapan
distrobox enter digi3 -- xdg-open https://example.com   # должен открыться пикер на хосте
```
