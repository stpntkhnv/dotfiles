# Словарь

Термины по порядку, каждый опирается только на те, что объяснены выше. Из
любого документа на термин при первом появлении ведёт ссылка вида
`[сокет](glossary.md#сокет)` — якорь совпадает с заголовком раздела ниже.

### Хост

Твоя настоящая машина. Arch Linux, который загрузился при включении. Всё
остальное, что упоминается в этой документации, живёт внутри него.

### Процесс

Запущенная программа. У процесса есть память, открытые файлы и права. Браузер
это процесс (точнее, несколько).

### Namespace

Механизм ядра Linux, который подменяет процессу его представление о системе.
Ядро одно, но процесс может видеть только часть того, что в нём есть.

Namespace бывают разных видов, и каждый подменяет что-то своё:

| Вид | Что подменяет |
|---|---|
| `mount` | какие файлы и каталоги видны |
| `pid` | какие процессы видны |
| `net` | какие сетевые интерфейсы, адреса и порты видны |
| `ipc` | общая память между процессами |
| `user` | какой пользователь ты с точки зрения ядра |

Ключевое: это не виртуальная машина. Ядро то же самое, процессор тот же,
никакой эмуляции. Просто ядро отвечает на вопросы «какие тут есть сетевые
интерфейсы?» по-разному в зависимости от того, кто спрашивает.

### Network namespace

Вид namespace из строки `net` в таблице выше, самый важный для изоляции
рабочих контекстов. Процесс в своём network namespace (сокращённо netns) имеет:

- собственный набор сетевых интерфейсов;
- собственную таблицу маршрутизации;
- собственный `127.0.0.1`;
- собственный набор занятых портов.

Последние два пункта неочевидны и разобраны отдельно ниже.

### Порт

Число от 1 до 65535. Программа, которая ждёт входящих соединений, «слушает»
какой-то порт. Веб-сервер обычно слушает 80 или 443. Порт существует внутри
одного network namespace: то, что слушает порт 8099 в одном namespace, никак
не связано с портом 8099 в другом.

### `127.0.0.1`

Адрес «эта же машина» (он же `localhost`, он же loopback). Соединение на него
никуда не уходит по проводу, оно замыкается внутри того же network namespace.

Отсюда следствие: `127.0.0.1` в контейнере и `127.0.0.1` на хосте — разные
вещи. Разные network namespace, разные loopback-интерфейсы. Если внутри
distrobox-контейнера что-то слушает `127.0.0.1:1080`
(`home/.chezmoiscripts/run_onchange_after_36-wsproxy-container.sh.tmpl`,
`ExecStart=/usr/bin/microsocks -i 127.0.0.1 -p 1080`), то хост, обратившись к
своему `127.0.0.1:1080`, туда не попадёт — он попадёт в свой собственный
loopback, где ничего нет.

### Сокет

Конец канала связи. Программа создаёт сокет, чтобы через него говорить с
другой программой. Один из двух видов — TCP-сокет — адресуется парой
«IP-адрес + порт», например `127.0.0.1:1080`. Он живёт в сетевом стеке, а
значит внутри своего network namespace.

### UNIX-сокет

Второй вид сокета. Адресуется не адресом и портом, а путём в файловой
системе, например `~/.local/share/wsproxy/digi3/socks.sock`
(`home/.chezmoiscripts/run_onchange_after_34-wsproxy-host.sh.tmpl`,
`SOCKDIR="{{ .chezmoi.homeDir }}/.local/share/wsproxy"`). Это файл особого
типа: `ls -l` показывает его с буквой `s` в начале прав доступа.

UNIX-сокет не находится в сетевом стеке вообще, он объект файловой системы.
Из этого следует главное свойство: два процесса могут общаться через
UNIX-сокет, даже если они в разных network namespace, при условии что оба
видят этот файл. Именно на этом построен мост между браузером на хосте и
сетью внутри distrobox-контейнера.

### Прокси

Посредник. Вместо того чтобы соединяться с сайтом самому, клиент соединяется
с прокси и говорит ему «сходи туда-то и принеси». Прокси идёт сам, своими
маршрутами, со своего адреса. Следствие: сайт видит адрес прокси, а не
адрес клиента, и маршрут до сайта строится из точки, где стоит прокси.

### SOCKS5

Конкретный протокол разговора с прокси. Работает на уровне соединений, а не
HTTP-запросов, поэтому годится для любого трафика. Разговор выглядит так:

```
клиент -> прокси:  привет, аутентификация не нужна
прокси -> клиент:  хорошо
клиент -> прокси:  соедини меня с example.com:443
прокси -> клиент:  соединил
                   дальше просто перекладываю байты в обе стороны
```

Число «5» — номер версии протокола.

### DNS и remote DNS

DNS превращает имя (`example.com`) в адрес. Без этого шага соединиться не с
чем. Вопрос в том, кто делает этот перевод: клиент или прокси.

Если резолвит клиент, резолвер видит все имена, которые тот открывает, а
внутренние имена, известные только DNS за прокси, не резолвятся вообще. Если
резолвит прокси — это называется remote DNS — имя уезжает к прокси как
текст и резолвится уже там; резолвер клиента не видит ничего. SOCKS5 умеет
передавать имя вместо адреса, SOCKS4 и HTTP-прокси — нет.

### Контейнер distrobox

Процесс (или группа процессов), запущенный в своём наборе namespace.
`podman` создаёт и запускает такие контейнеры, `distrobox` — надстройка над
podman, которая пробрасывает домашний каталог, графику, звук и даёт команду
`distrobox enter`. Проверить, что namespace действительно разные:

```sh
readlink /proc/self/ns/net                          # хост
distrobox enter digi3 -- readlink /proc/self/ns/net # контейнер
```

Числа в скобках будут разные — это идентификаторы namespace в ядре.

### Контейнер Firefox

Не путать с контейнером distrobox — тот же термин, совсем другая сущность.
Firefox container — изолированная банка состояния внутри одного браузера:
свои куки, свой localStorage, свои сессии, свой кеш авторизации. Вкладка
принадлежит одному контейнеру, и для сайта два контейнера выглядят как два
разных человека. У каждого такого контейнера есть `cookieStoreId` вида
`firefox-container-7`, список хранится в профиле браузера
(`~/.config/zen/*/containers.json`).

### Space в Zen

Раскладка Zen: свой набор вкладок, своя тема, свои закреплённые вкладки. Про
сеть и куки space не знает ничего. Space можно привязать к контейнеру Firefox
— тогда новые вкладки в этом space открываются в нём, но эту связь создают
руками, автоматически её нет.

### Профиль браузера

Каталог со всем состоянием браузера целиком: настройки, расширения, история,
все контейнеры Firefox. Профили видны в `about:profiles`. В интерфейсе Zen
кнопка привязки space к контейнеру называется «Set Profile», хотя выбирает
она контейнер, а не профиль — неудачное название, источник постоянной
путаницы.

### Systemd unit

Единица работы systemd: описание того, что запускать и при каких условиях.
Юнит вида `.service` описывает один процесс-демон. В этом репозитории юниты
живут по обе стороны моста между хостом и контейнером:
`home/.chezmoiscripts/run_onchange_after_34-wsproxy-host.sh.tmpl` пишет
пользовательский юнит `wsproxy-<контекст>.service` в
`~/.config/systemd/user/`, а
`home/.chezmoiscripts/run_onchange_after_36-wsproxy-container.sh.tmpl` пишет
системные юниты `wsproxy-socks.service` и `wsproxy-bridge.service` внутри
контейнера в `/etc/systemd/system/`.

### Systemd slice

Юнит вида `.slice` — не процесс, а ограничение ресурсов для группы процессов.
`home/dot_config/systemd/user/browser.slice` задаёт общий бюджет памяти
(`MemoryHigh=6G`, `MemoryMax=8G`) для всех браузеров разом, а
`home/dot_config/systemd/user/browser-zen.slice` — бюджет поменьше для одного
Zen. Через дефис в имени systemd делает `browser-zen.slice` дочерним по
отношению к `browser.slice`, поэтому цифры зонтика — общий потолок независимо
от того, сколько браузеров открыто одновременно.

### Шаблон chezmoi

Файл с расширением `.tmpl`, который chezmoi прогоняет через движок шаблонов
Go перед тем, как положить результат в домашний каталог или выполнить как
скрипт. Внутри `{{ }}` — переменные и условия из `home/.chezmoidata.yaml` и
других источников данных chezmoi. Проверить, во что раскроется конкретный
шаблон, можно без применения всей конфигурации:

```sh
chezmoi execute-template < home/.chezmoiscripts/run_onchange_before_20-packages.sh.tmpl
```

### `run_onchange`

Часть имени скрипта в `home/.chezmoiscripts/`, которая говорит chezmoi,
когда его перезапускать. Скрипт с `run_onchange_` в имени выполняется заново
только тогда, когда изменился текст самого скрипта после подстановки
переменных шаблона (`docs/features.md`, раздел «Два вида скриптов»). Скрипт
без `onchange` (`run_after_...` или `run_before_...`) выполняется на каждом
`chezmoi apply` и годится там, где нужно перепроверять состояние машины, а не
только текст скрипта.

### Pathspec

Грамматика путей, которую понимает git, в частности `git ls-files --
<pattern>`. В этом репозитории это единственная допустимая грамматика для
`covers.paths` в шапках документов: звёздочка `*` пересекает `/`, а фигурные
скобки вида `{a,b}` git не раскрывает (это делает bash), поэтому запись,
работающая в одном месте, в другом промахивается молча. Каждый файл — своя
строка.
